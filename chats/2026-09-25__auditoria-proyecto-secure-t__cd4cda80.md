Dado tu perfil (Pedro Belentani), tu necesidad de eficiencia, validación científica, uso de agentes autónomos y sensibilidad a la sobrecarga cognitiva, este plan está diseñado para ser ejecutado mediante **agentes AI orquestados**, minimizando tu intervención manual a solo puntos de control críticos (gates).

# 🛡️ AUDITORÍA PRELIMINAR Y DIAGNÓSTICO (Estado Actual: ~45/100)

### 1. Estado de los Componentes
*   **Frontend (Campus):** ✅ **Operativo.** React 19 + Vite desplegado en Netlify/Vercel. Matrícula anónima funcional (`/enroll`). UI responsiva y accesible.
*   **Backend (API Core):** ⚠️ **Parcial.** Lógica escrita en Express/Node, pero actualmente *no desplegada* en entorno serverless productivo real (se simula o corre en Docker local/Railway). Las rutas `/api/*` devuelven 404 en el frontend estático si no hay proxy correcto.
*   **Base de Datos:** ⚠️ **Local/Híbrida.** Esquema Drizzle definido, pero falta una instancia PostgreSQL gestionada, persistente y con backups automáticos en producción conectada al backend vivo.
*   **Seguridad:** 🟡 **En Proceso.** `SECURITY.md` existe, headers básicos configurados, pero falta pentesting automatizado continuo, WAF (Web Application Firewall) activo y gestión de secretos rotativos en producción.
*   **IA & Agentes:** 🟡 **Prototipo.** Gateway definido, integración con Groq/Supabase, pero falta la capa de "Gobernanza Autónoma" (auto-corrección, auto-escalado de contextos RAG).
*   **Laboratorios (Cyber Range):**  **Pendiente Crítico.** La arquitectura está definida (`labs/`), pero los entornos aislados (Docker-in-Docker o Firecracker microVMs) no están activos para ejecución de código de estudiantes.
*   **Duplicidad:** Detectados repositorios espejo (`secure-t-v2`, `secure-t-app`, `secure-t-university`). **Acción requerida:** Consolidación inmediata para evitar deriva de código (code drift).

### 2. Requisitos Técnicos Obligatorios (El "Must-Have")
Para pasar a producción nivel enterprise/académico:
*   **Lenguaje Principal:** TypeScript 5.6+ (Strict Mode obligatorio).
*   **Runtime:** Node.js 22+ (LTS).
*   **Gestor de Paquetes:** `pnpm` (v12+) para monorepos eficientes y deduplicación.
*   **Base de Datos:** PostgreSQL 16+ con extensiones `pgvector` (para RAG) y `pgcrypto`.
*   **ORM:** Drizzle ORM (Type-safe, migraciones atómicas).
*   **Infraestructura:** Docker Compose (local), Kubernetes o PaaS (Railway/Render/Fly.io) para prod.
*   **CI/CD:** GitHub Actions (Flujos: Lint -> Test -> Build -> Security Scan -> Deploy).
*   **Testing:** Vitest (Unitario), Playwright (E2E), OWASP ZAP (Seguridad).
*   **Autenticación:** Supabase Auth o Custom JWT con HMAC (tokens anónimos firmados ya implementados,需 escalar a RBAC completo).

# 🚀 PLAN DE EJECUCIÓN DETALLADO (PASOS 1 AL 100)

Este plan está dividido en **Fases**. Cada fase contiene pasos atómicos. Puedes asignar cada fase a un agente AI diferente (ej. Agente de Infraestructura, Agente de Seguridad, Agente Académico).

## FASE 1: CONSOLIDACIÓN Y LIMPIEZA (Pasos 1-15)
*Objetivo: Eliminar ruido, unificar repositorios y asegurar la base del código.*

1.  **Auditoría de Repositorios:** Identificar `secure-t` (Principal) como fuente de verdad. Archivar o eliminar `secure-t-v2`, `secure-t-app`, `secure-t-university` tras verificar que no tengan commits únicos no fusionados.
2.  **Unificación de Branches:** Establecer estrategia GitFlow estricta: `main` (prod), `develop` (staging), `feature/*` (dev). Proteger rama `main` con reglas de PR obligatorias.
3.  **Limpieza de Dependencias:** Ejecutar `pnpm dedupe` y actualizar todas las dependencias a sus últimas versiones estables compatibles con Node 22.
4.  **Estandarización de `.env`:** Unificar `.env.example` cubriendo variables locales, de staging y de producción. Validar que ningún secreto esté hardcodeado.
5.  **Refactorización de Imports:** Asegurar que todos los imports usen rutas absolutas o alias definidos en `tsconfig.json` para evitar errores de resolución en monorepo.
6.  **Validación de Tipos Global:** Ejecutar `tsc --noEmit` en todo el workspace. Corregir cualquier `any` implícito. El código debe ser 100% tipado.
7.  **Configuración de Linting Estricto:** Actualizar `.eslintrc` y `.prettierrc` para seguir estándares de seguridad (ej. prohibir `eval`, exigir manejo de errores).
8.  **Documentación de Arquitectura (ADR):** Revisar `docs/` y asegurar que cada decisión técnica tenga un ADR (Architecture Decision Record) actualizado.
9.  **Eliminación de Código Muerto:** Usar herramientas como `knip` o `ts-prune` para identificar y borrar archivos/componentes no utilizados.
10. **Normalización de Commits:** Configurar husky hooks para forzar "Conventional Commits" antes de cada push.
11. **Licencias:** Verificar `LICENSE` y `NOTICE-ATRIBUCIONES.md` para asegurar cumplimiento AGPL-3.0 en todos los módulos.
12. **Setup de Workspace Monorepo:** Asegurar que `package.json` raíz gestione correctamente los workspaces (`client`, `server`, `ai`, `academic`, etc.).
13. **Contenedores Base:** Optimizar `Dockerfile` multi-stage para reducir imagen final (<200MB si es posible).
14. **Variables de Entorno Críticas:** Definir rotación automática de claves API (Groq, Supabase) en el gestor de secretos del proveedor cloud.
15. **Checkpoint 1:** Commit etiquetado `v1.1-consolidated`. CI verde.

## FASE 2: INFRAESTRUCTURA Y DESPLIEGUE BACKEND (Pasos 16-35)
*Objetivo: Llevar el backend de "local/Docker" a "Producción Real Alta Disponibilidad".*

16. **Selección de Proveedor Cloud:** Decidir entre Railway, Render, Fly.io o AWS ECS (Recomendación: Railway o Fly.io por facilidad con Docker y Postgres nativo).
17. **Provisionamiento de Base de Datos:** Crear instancia PostgreSQL gestionada con backups diarios y punto de recuperación (PITR). Habilitar extensión `pgvector`.
18. **Configuración de Red Privada:** Aislar la BD en red privada, accesible solo por el servicio backend.
